3.1 為什麼需要分支

多人開發不可能都直接改 main——不然 A 改到一半，B 的變更就疊上來，亂成一團。分支（branch）讓每個人、每個功能在平行的軌道上開發，互不干擾，最後再合併（merge）回主線。

分支示意 · DIAGRAM
main:     o──o──────────o──────o
               \        / 合併
feature:        o──o──o

主線（main）永遠「穩定可用」；功能在 feature 開發，完成後合併回 main。
核心原則：main 要保持「隨時可部署」；一切新東西都先放分支。

3.2 原理：分支只是「指向 commit 的指標」

Git 的歷史是一條commit 鏈。分支本質上只是一個會移動的指標（pointer），指向某個 commit；HEAD 則指向「你現在站在哪個分支」。所以建立分支幾乎零成本——只是做個書籤。

概念 · CONCEPT
o──o──o──o──o            (main)
        └─────o──o        (feature)

HEAD → feature（目前正在 feature 上工作）
main  → 仍停在「分叉前」的 commit
這解釋了為什麼切換分支那麼快、那麼安全——你只是移動書籤，不是複製檔案。Git 之所以強，就強在「歷史是 DAG、分支是書籤」。

3.3 分支操作指令

常用指令 · COMMANDS
git branch feature-login      # 建立分支
git checkout feature-login    # 切換到該分支
git checkout -b feature-x     # 建立並切換（最常用）
git branch                    # 列出所有分支（* 標示目前位置）
git branch -a                 # 連遠端分支一起列
git branch -d feature-x       # 刪除已合併的分支
命名慣例：用「斜線語意」一眼看懂用途——feature/login、fix/typo、chore/deps、docs/readme。

3.4 合併 · Merge

把某分支的變更併進「目前所在的分支」。Git 會試著自動合併；只有兩邊改了同一行才需要你出手。

合併流程 · COMMANDS
git checkout main              # 回到主線
git pull                       # 先取得最新（好習慣）
git merge feature-login        # 把功能分支合併進來
git push                       # 上傳合併結果
成功合併 · NO CONFLICT

✅ Merge made by the 'ort' strategy.
兩邊改的是「不同檔案 / 不同區段」→ Git 自動完成。

衝突 · CONFLICT

⚠️ CONFLICT (content): Merge conflict in app.py
兩邊改了同一行 → 需要你手動解決。

3.5 Pull：fetch + merge

團隊協作時，動手前先 git pull 拿別人推的新東西。git pull 其實是兩步的縮寫：

Pull 的意義 · EXPLAINED
git pull = git fetch + git merge
   fetch：把 GitHub 的資料抓下來（不影響工作區）
   merge：併入你的目前分支
好習慣：每次開始工作前 git pull，能大幅減少後面的衝突——這是最便宜、最有效的協作規矩。

3.6 衝突 · Conflict 的產生與解決

當兩邊改了同一行程式碼，Git 不知道該留哪邊，就產生衝突——這不是錯誤，是 Git 在請你「做人工判斷」。先看懂標記：

衝突標記 · CONFLICT MARKS
<<<<<<< HEAD          # 目前分支（main）的版本
price = 100
=======                 # 分隔線
price = 120
>>>>>>> feature-x    # 被合併分支的版本

解決步驟：

  1. 打開衝突檔案，找到 <<< / >>> 標記。
  2. 決定保留哪邊（或兩邊都留），刪掉三行標記。
  3. git add 該檔案。
  4. git commit 完成合併（不要自己寫 merge message 也行，Git 會給預設）。
衝突不是壞事：代表兩個人都動了同一處——「必須人工判斷」是正常的。維持小 commit、頻繁 pull、同一區域少人同時改，衝突就會又少又好解。

3.7 把分支推上 GitHub

推分支 · COMMANDS
git push -u origin feature-login   # 第一次推新分支
git push                           # 之後直接推

推到 GitHub 後，下一步通常就是開一個 Pull Request——下一單元的主題。

3.8 Worked Example：完整分支開發

練習 · PRACTICE
git checkout -b feature/greeting
echo "print('hello')" >> app.py
git add app.py
git commit -m "feat: add greeting"
git checkout main
git pull
git merge feature/greeting
git push
git branch -d feature/greeting   # 合併完可刪
驗收 · ACCEPT

✅ 分支建立／切換成功
✅ main 合併後含新內容
✅ git log --graph --oneline 看得到合併
✅ 已刪除合併完的分支

進階練習：故意製造一次衝突——在兩個分支分別把 app.py 同一行改成不同值，再 merge，練習走完「看標記 → 人工判斷 → add → commit」四步。
看完這單元你應該能說出：
  • 解釋分支的原理（指向 commit 的指標）與為什麼需要分支。
  • 寫出建立、切換、列出、刪除分支的指令。
  • 說出 merge、pull（fetch + merge）的意義與關係。
  • 看懂衝突標記並獨立完成一次衝突解決。
  • 遵守「動手前先 pull、小步提交」的協作好習慣。

3.9 進階真實情境 Worked Example：Rebase 工作流 + 衝突排解 + bisect 找壞 commit

情境 · SCENARIO
你是維護者，feature 分支落後 main 20 個 commit。
合併會產生一個醜的合併節點，你決定用 rebase。
rebase 過程中遇到衝突，排解後繼續。
然後發現 main 的某個 commit 壞了某功能，
用 bisect 找出是哪一個。
完整操作 · COMMANDS
# 1. 同步上游並 rebase
git fetch origin
git checkout feature/dark-mode
git rebase origin/main

# 2. 衝突出現：app.py 第 42 行
#    用 git diff 看衝突檔案
git diff
#    手動編輯後：
git add app.py
git rebase --continue  # 繼續（不要 git commit！）

# 3. rebase 完成，push
git push origin feature/dark-mode --force-with-lease

# 4. 開 PR → 用 Squash merge
#    歷史乾淨，完全線性

# 5. 找出哪個 commit 壞了某功能（bisect）
git bisect start
git bisect bad       # 目前 commit 壞了
git bisect good v1.0 # v1.0 還正常

# 6. Git 每次跳一半，你測試後標記
#    測試指令（跑一次就知道好壞）：
npm test
git bisect good  # 或 git bisect bad

# 7. 找到後：
git bisect reset
為什麼選這個方法：Rebase 保持歷史完全線性（沒有合併節點），搭配 Squash merge 在 PR 階段壓成一筆——最後的 main 歷史讀起來就像一本書的目錄。bisect 用二分搜尋法在 O(log n) 步驟內定位到壞 commit，比肉眼看 log 快 100 倍。

3.10 深入原理擴充

Merge vs Rebase 的 DAG 差異
Merge（保留歷史完整）：
main:     A──B──C───────M──────
                \       /
feature:         D──E──F

M = merge commit（有兩個 parent）

Rebase（重寫歷史）：
main:     A──B──C──────────────
                    \
feature:             D'──E'──F'
                     (commit hash 改了！)
  • Rebase 原理：把 feature 分支的每一個 commit「重放（replay）」到 main 的最新節點之上。每個 commit 會產生新的 hash（D' ≠ D），所以是「重寫歷史」。
  • Reflog：即使 rebase 重寫了歷史，git reflog 會記錄你每一次操作前後的 HEAD 位置——「Git 永遠能救回資料」的秘密武器。
  • Protected Branch 的 rebase 限制：GitHub 保護分支上直接 rebase 會被擋，因為 rebase 改了 commit hash，會導致已 push 的分支與遠端不一致。

3.12 進階挑戰題

  1. 在一個 repo 裡建立 feature-A 和 feature-B 兩個分支，各自修改不同檔案，然後同時 merge 回 main——觀察 Git 如何處理「無衝突的並行修改」。再故意在兩個分支改同一行，練習手動解決衝突。
  2. 用 git rebase -i（interactive rebase）把一個分支上最近 5 個 commit 合併成 2 個——練習 pick、squash、reword、fixup 的差異。
  3. 研究 git cherry-pick 的使用場景（只拿某分支的特定 commit），實際在兩個分支間 cherry-pick 一個 commit 並觀察 DAG 變化。
