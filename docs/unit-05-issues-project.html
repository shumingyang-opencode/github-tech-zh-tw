5.1 定義：Issue 是什麼

Issue 是「一件事」的討論單：可以是 bug、新功能、問題，或任何待辦。每個 issue 有獨立編號（#12），可留言、指派、加標籤、掛里程碑。它把「要做的事」變成可追蹤、可分工、可關聯的物件。

Issue 寫法 · FORMAT
標題：登入頁在 Safari 上空白
描述：
  步驟再現：
  1. 開啟 Safari
  2. 到 /login
  3. 畫面空白
  預期：顯示登入表單
  環境：Safari 17, macOS 14
好 Issue 的四要素：「標題一行講清」＋「步驟可再現」＋「預期 vs 實際」＋「環境/版本」。讓看到的人不用問就能動手。

5.2 Issue Template：讓大家填得一致

把常見的 Issue 結構存成模板，放在 .github/ISSUE_TEMPLATE/，開新 issue 時就能選用：

.github/ISSUE_TEMPLATE/bug.yml · 片段
name: Bug report
description: 回報一個問題
body:
  - type: textarea
    attributes:
      label: 步驟再現
      placeholder: 1. ... 2. ...
  - type: dropdown
    attributes:
      label: 嚴重程度
      options:
        - 低
        - 中
        - 高

也支援簡單的 Markdown 版（bug_report.md）。模板能大幅提升回報品質，開源專案必備。

5.3 Labels · 標籤分類

用顏色標籤把 issue 分類，一眼看出性質：

常見標籤 · LABELS
bug             # 紅：壞掉了
enhancement     # 藍：新功能
good first issue # 綠：適合新手（開源徵才用）
help wanted     # 綠：徵求協助
documentation   # 灰：文件
搜尋神技：用 is:issue label:"good first issue" 就能在全站篩出「適合你第一筆貢獻」的 issue（單元 8 會再用）。

5.4 Milestones · 里程碑

把一群 issue 歸到一個「里程碑」，設定截止日，追蹤整體進度：

Milestone 範例 · EXAMPLE
v1.0 發布  （截止：2026-10-01）
  ├─ #10 修復登入 bug    （open）
  ├─ #12 新增搜尋        （open）
  └─ #15 文件更新        （closed）
  進度：1/3 完成

里程碑對齊「版本發布」最有用——讓「這版要交付什麼」一目了然。

5.5 Projects · 看板專案

類似 Trello 的看板，用欄位（To do / In progress / Done）拖曳管理卡片。卡片可來自 issue，合併後自動移動（用自動化規則）：

看板 · BOARD
┌─ To do ──┬─ In progress ──┬─ Done ──┐
│ #10 修bug│ #12 新增搜尋    │ #15 文件 │
│ #18 測試 │                 │          │
└──────────┴─────────────────┴──────────┘
卡片可來自 Issue，合併後自動移動（用自動化規則）。
分工：Labels 是「分類」，Milestones 是「時間與版本」，Projects 是「當下狀態（看板）」。三者互補，不衝突。

5.6 Discussion 與 Wiki

工具適合vs Issue
Issues任務、bug、具體待辦「要做的事」，需要解決
DiscussionsQ&A、想法、公告、功能發想「開放討論」，不一定要轉任務
Wiki使用手冊、設計文件等長內容「文件」，不是討論

5.7 把 Issue 與 PR 連起來

完整的工作流循環：

工作流 · WORKFLOW
1. 開 Issue（描述任務/bug）
2. 開分支 → 開發 → 開 PR
3. PR 描述寫「Closes #12」
4. 合併 → Issue 自動關閉
5. 看板/里程碑進度自動更新

這樣每一行程式碼都能追溯回「最初的需求或 bug」——這就是業界說的可追溯性（traceability）。

5.8 Worked Example：為你的專案建立追蹤系統

練習 · PRACTICE
1. 開 3 個 issue：bug、新功能、文件
2. 建立 labels：bug / enhancement / docs
3. 建立 milestone「v1.0」並掛上 issue
4. 建一個 Project 看板，把 issue 拖進去
5. 用 PR 關閉其中一個 issue（Closes #xx）
驗收 · ACCEPT

✅ Issues 有標籤與里程碑
✅ 看板顯示正確狀態
✅ 合併 PR 後 issue 自動關閉
✅ label:"good first issue" 能搜到你的項目

練習：為你的 repo 加上 bug.yml issue template，實際開一支 issue 測試欄位與選單是否正確。
看完這單元你應該能說出：
  • 說明 Issue 的定位與「好 Issue」的四要素。
  • 用 Issue template 建立一致的填寫格式。
  • 說出 Labels / Milestones / Projects 各自管理什麼。
  • 建立「Issue → 分支 → PR → Closes」的完整工作流循環。
  • 區分 Discussions、Wiki 與 Issues 的用途。

5.9 進階真實情境 Worked Example：用 GitHub API 批次建立 Issue + Project 自動化

情境 · SCENARIO
你是一個專案的 Tech Lead，
需要把產品需求文件（PRD）轉化為
20 個 Issue，建立 Project 看板，
設定自動化規則：
- Issue 開啟 → 自動加 label
- PR 合併 → 自動移到 Done
- 每週五自動發送進度摘要
完整操作 · COMMANDS
# 1. 批次建立 Issues（gh CLI 陣列）
titles=(
  "使用者登入功能"
  "密碼重設流程"
  "個人資料頁面"
  "搜尋功能"
  "匯出 CSV"
)

for t in "${titles[@]}"; do
  gh issue create \
    --title "$t" \
    --label "enhancement" \
    --project "v2.0 Launch" \
    --body "需求來源：PRD section 2"
done

# 2. 建立 Milestone
gh api --method POST \
  "/repos/TechCo/app/milestones" \
  -f title="v2.0" \
  -f due_on="2026-12-01T00:00:00Z"

# 3. 用 Project 自動化規則
gh api --method POST \
  "/orgs/TechCo/projects" \
  -f name="v2.0 Launch" \
  -f body="Product launch tracking"

# 4. 建立自動化規則（Webhook 觸發）
# 設定路徑：Project → Settings → Workflows
# Rule: Issue opened → Add to project
# Rule: PR merged → Move to Done

# 5. 每週進度摘要（用 Discussion + gh CLI）
gh api --method POST \
  "/repos/TechCo/app/discussions" \
  -f title="Weekly Status - $(date +%Y-%m-%d)" \
  -f body="## v2.0 進度\n\n$(gh issue list \
    --project 'v2.0 Launch' --json number,title,state \
    --jq '.[] | "- [\(if .state=="OPEN" then " " else "x" end)] #\(.number) \(.title)"')"
為什麼選這個方法：用 gh API 批次操作比在 UI 上逐個建立快 50 倍，而且可版本化（整個腳本放進 repo 的 scripts/ 資料夾）。自動化規則讓「流程不用人盯」，維護者專注在決策而非瑣事。

5.10 深入原理擴充

GitHub Issues 資料模型
Issue（獨立討論單）
├── Number（自動編號，不可變更）
├── Title + Body（Markdown）
├── Labels[]（多對多）
├── Assignees[]（多對多）
├── Milestone（多對一）
├── Project（多對多）
├── Timeline（事件序列）
│   ├── Comment（留言）
│   ├── Cross-reference（關聯 PR / Issue）
│   └── Commit / PR merge 事件
└── State（open / closed）
  • Issue 編號唯一性：Issue 和 PR 共享同一個號碼池——Issue #10 之後的 PR 可能是 #11，這是正常的。
  • Cross-reference：在 PR 描述寫 #42 或 Fixes #42，GitHub 會在 Issue 的 Timeline 自動建立關聯，點擊可跳轉。
  • Issue Template 的進階用法：YAML 表單格式（.github/ISSUE_TEMPLATE/bug.yml）支援下拉選單、核取方塊、必填欄位，比 Markdown 格式更結構化。
  • Projects v2：新版 Projects 支援 Table View、Chart View（長條圖/圓餅圖）、Custom Fields（優先級、Sprint、成本），比舊版看板強大得多。

5.12 進階挑戰題

  1. 為你的 repo 建立三種 Issue Template（Bug Report / Feature Request / Documentation），用 YAML 表單格式，包含必填欄位、下拉選單和核取方塊。開一個 Issue 測試模板是否正常運作。
  2. 用 gh CLI 建立一個 Project（v2），包含自訂欄位（Priority: High/Medium/Low、Sprint: Week 1-4），然後批次建立 10 個 Issue 並指派不同 Priority。
  3. 研究 GitHub Discussions 的「分类（Categories）」功能，設計一個分類架構（Q&A / Ideas / Show and Tell / Announcements），寫一段說明為什麼 Discussions 比 Issue 更適合某些場景。

5.13 專案級端到端 Worked Example：開源社群 Issue 治理專案

單元 5.9 用 API 批次建了 20 個 Issue；這裡把 Issue 制度放大成整個專案的可持續治理——模板、標籤、里程碑、自動分診（triage）、每週摘要。讓「開源專案每天湧進的 Issue」不會淹沒維護者——這是單元 5.9「一次性操作」之上的制度設計。

產出檔案樹 · FILE TREE
techco-app/
├── .github/
│   ├── ISSUE_TEMPLATE/
│   │   ├── bug.yml            # Bug 表單（必填欄位）
│   │   ├── feature.yml        # 功能請求
│   │   └── config.yml         # 封鎖空白 Issue
│   └── workflows/
│       ├── triage.yml         # 新 Issue 自動加 label / 指派
│       └── weekly-summary.yml # 每週一發進度摘要
├── docs/
│   └── triage-guide.md        # 維護者分診 SOP
└── CONTRIBUTING.md            # 指引貢獻者去哪開 Issue
關鍵檔案 · KEY FILES
# .github/ISSUE_TEMPLATE/bug.yml（片段）
name: Bug report
description: 回報問題
body:
  - type: textarea
    attributes:
      label: 步驟再現
    validations:
      required: true
  - type: dropdown
    attributes:
      label: 嚴重程度
      options: [低, 中, 高]

# .github/workflows/triage.yml（片段）
on:
  issues: { types: [opened] }
jobs:
  triage:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.addLabels({
              owner, repo, issue_number,
              labels: ["needs-triage"]
            })
驗證命令與輸出 · VERIFY
# 1. 新 Issue 自動被加 needs-triage
gh issue create --title "登入壞了" --body "..."
gh issue view 1 --json labels --jq '.labels[].name'
# 輸出 → needs-triage

# 2. 里程碑進度
gh api /repos/TechCo/app/milestones \
  --jq '.[] | "\(.title): \(.open_issues)/\(.closed_issues)"'
# 輸出 → v2.0: 3/12

# 3. 每週摘要 workflow 產出的 Discussion
gh api "/repos/TechCo/app/discussions" \
  --jq '.[] | select(.title|startswith("Weekly")) | .title' | head -1
# 輸出 → Weekly Status - 2026-08-17
為什麼這是「專案級」：單元 5.9 是一批一次性操作；這裡是「讓 Issue 流程自己跑」的制度。模板決定輸入品質、triage 決定優先序、週報決定透明度——真正的大型專案靠制度 + 自動化維持秩序，而不是靠維護者熬夜。

5.14 效能 / 品質 / 安全深度

效能 · PERFORMANCE
- API 批次操作：一次迴圈建完，別逐筆點 UI
- Webhook 即時觸發，triage 零延遲
- Projects v2 自動化規則：卡片自動移動
- 里程碑別掛太多 Issue：粒度適中才好追蹤
- 大專案用 GraphQL API 一次撈多欄位，省 rate limit
品質 · QUALITY
- 模板決定輸入品質：必填欄位 + 下拉選單
- 分診 SLA：新 Issue 48 小時內回覆
- 標籤體系標準化（bug / enhancement / needs-triage）
- 里程碑對齊版本 → 交付範圍透明
- triage-guide 寫成 SOP，任何維護者都能接手
安全 · SECURITY
- Issue 內容不要貼 secrets / 個資
- 自動化 bot 的 token 用最小權限
- 避免讓社群成員誤觸敏感 label / 權限
- 注意 Markdown 注入：不要渲染未受信任的 HTML
- 安全問題（漏洞）請使用者走 SECURITY.md 私訊管道
