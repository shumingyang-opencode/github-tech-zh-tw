8.1 開源是什麼

開源（Open Source）＝原始碼公開、任何人可看、可用、可改、可再散布（依授權條款）。GitHub 上絕大多數 repo 都是開源的。你從「使用者」變成「貢獻者（contributor）」的旅程，就在這一單元。

先講法律：「原始碼公開」≠「可以隨意使用」。合法範圍完全由 LICENSE（授權）決定。

8.2 LICENSE：沒有它 = 不能合法使用

沒有 LICENSE 的 repo，法律上別人不能合法使用你的程式碼（著作權默認保留）。開源專案一定要放。常見選擇：

授權特點
MIT最寬鬆：幾乎隨你用，附授權聲明即可
Apache-2.0寬鬆 + 專利授權保障
GPL-3.0改作也必須開源（copyleft）
CC-BY-4.0內容/文件用（本站就是用這個）

不確定選哪個？用 choosealicense.com 引導。也可在 GitHub 建 repo 時直接選 License。

8.3 CONTRIBUTING.md：貢獻規範

告訴貢獻者「怎麼參與」——是開源專案的門檻文件。大綱：

CONTRIBUTING.md · 大綱
# 貢獻指引
1. 如何回報 bug（找哪個 issue 模板）
2. 如何提功能請求（先開 Discussion？）
3. 開發流程（branch 命名、commit 格式、測試）
4. 程式碼風格（lint / format）
5. Review 流程（誰審、多久回應）
6. 行為守則（指向 CODE_OF_CONDUCT）
為什麼重要：一份清楚的 CONTRIBUTING 能讓「第一次貢獻」的人不必問東問西，直接上手——好維護者從降低貢獻門檻開始。

8.4 CODE_OF_CONDUCT：行為守則

規定社群互動的底線（尊重、不騷擾、包容）。GitHub 有內建模板（Contributor Covenant 最常見）。它宣示「這個專案歡迎所有人」，也是發生紛爭時的處理依據。

8.5 Release：發佈版本

用 tag 標記某個 commit 為「正式版本」，再建立 Release（含發佈說明與附件）：

發佈流程 · RELEASE
1. 確定 main 通過所有 CI
2. 建立 tag：git tag v1.0.0 && git push --tags
3. GitHub → Releases → Create a new release
4. 選 tag、寫 Release Notes（變更摘要）
5. 可附上建置產物（source code / binary）

語意化版本（SemVer）：主版.次版.修訂——v2.1.0：主版（不相容變更）、次版（新增功能）、修訂（bug 修正）。遵守它，使用者才知道升級會不會壞。

Release Notes · 範例
## v1.2.0 (2026-09-01)

### ✨ 新增
- 支援暗色模式
- 新的匯出格式

### 🐛 修正
- 修正登入頁在 Safari 的空白問題

### ⚠️ 破壞性變更
- 最低 Node 版本升至 18
拆解 · ANATOMY

① 版本號＋日期
② 依類型分節（新增/修正/破壞）
③ 破壞性變更一定要註明
④ emoji 讓掃讀更快
⑤ 用 gh 快速發佈：gh release create v1.2.0 --generate-notes

自動生成：gh release create v1.2.0 --generate-notes 會依「該版本以來的 PR 標題」自動產生 Release Notes，再人工微調即可。

8.6 貢獻流程：Fork → 開發 → PR

Fork = 把別人的 repo「複製一份到你的帳號」，你就可以隨意改，再發 PR 貢獻回去：

Fork 工作流 · WORKFLOW
1. 瀏覽某 repo → 右上角 Fork
2. clone 你的 fork：
   git clone https://github.com/你/原repo.git
3. 加「上游」remote（原專案）：
   git remote add upstream https://github.com/原作者/原repo.git
4. 開分支 → 改 → push → 開 PR
   （PR 方向：原 repo 的 base ← 你的 fork 分支）
同步上游：開發前 git fetch upstream && git merge upstream/main，把原專案最新進度同步進來，避免 PR 衝突。這步忘了，衝突就來了。
第一次貢獻 · FIRST CONTRIBUTION
1. 找 label:"good first issue" / "help wanted"
2. 先留言「我想做這個」，確認再動手
3. 讀 CONTRIBUTING.md
4. 小步提交、寫清楚 commit message
5. 開 PR，耐心回覆 review 意見
從小的開始：改錯字、修文件、加測試都是極好的第一筆貢獻——README 修一個連結，就完成一次真實開源貢獻。

8.7 社群經營 · 維護者的習慣

  • README 品質：一句話、徽章、安裝、使用、截圖——決定陌生人留不留步。
  • 回應 Issue / PR：即使暫時無法處理，回一句「感謝回報，已加入 backlog」也很有價值。
  • 用 label 管理：good first issue、help wanted 讓新手找得到事做。
  • 自動化接手：Dependabot 開的 PR、CI 的 status check，幫你守住品質。

8.8 社群禮儀與安全

類別做法
禮儀先搜再問（查 Issues / Discussions）；Issue 給完整資訊；被拒別氣餒；語氣友善、感謝維護者
安全Secrets 用 GitHub Secrets（單元 7）；Dependabot 掃依賴漏洞；Code scanning 掃程式；簽署 commit（GPG/SSH）；保護分支；Secret scanning 偵測洩漏 Token
紅線：repo 出現意外洩漏的 Token/金鑰 → ① 立即到設定撤銷該憑證；② 用 git filter-repo 清理歷史；③ 通知 GitHub support。撤銷永遠比清理更重要。

8.11 進階真實情境 Worked Example：從 Fork 到上游合併的完整開源貢獻

情境 · SCENARIO
你要為一個熱門開源專案（如 VS Code）貢獻一個功能：
1. Fork + clone
2. 建立開發環境
3. 開分支開發
4. 同步上游最新
5. 開 PR + 回覆 review
6. 合併後清理
完整操作 · COMMANDS
# 1. Fork（用 gh CLI）
gh repo fork microsoft/vscode --clone

# 2. 加上游 remote
cd vscode
git remote add upstream \
  https://github.com/microsoft/vscode.git
git remote -v
# origin    → 你的 fork
# upstream  → 原專案

# 3. 建立開發分支
git checkout -b feature/new-snippet-language

# 4. 開發（以小步提交）
git add src/vs/editor/contrib/snippet/
git commit -m "feat: add rust snippet support"

# 5. 同步上游（開發前做）
git fetch upstream
git rebase upstream/main
# 衝突？解完後 git rebase --continue

# 6. 推送到你的 fork
git push origin feature/new-snippet-language

# 7. 開 PR（用 gh CLI）
gh pr create \
  --repo microsoft/vscode \
  --title "feat: Add Rust language snippets" \
  --body "$(cat <<'EOF'
## Description
Adds Rust language snippet definitions.

## Changes
- New file: `rust.json` snippet definitions
- Updated language configuration

## Testing
- Verified snippets appear in VS Code
- No linting errors

Closes #99999
EOF
)" \
  --reviewer username1,username2

# 8. 回覆 review 意見
gh pr comment 12345 --body "Thanks for the review! Updated in commit abc123."

# 9. 合併後清理
git checkout main
git pull upstream main
git branch -d feature/new-snippet-language
git push origin --delete feature/new-snippet-language
為什麼選這個方法：gh CLI 讓你在終端機完成整個貢獻流程——不用切到瀏覽器、不用手動填表單。同步上游（fetch + rebase）確保你的 PR 基於最新程式碼，減少衝突機率。最後清理遠端分支是「禮貌」——維護者不用看到你已合併的舊分支。

8.12 深入原理擴充

開源安全鏈
程式碼安全 · SECURITY CHAIN
├── Commit Signing（GPG / SSH）
│   └── git commit -S → 簽署 commit，防偽造
│
├── Secret Scanning（GitHub 內建）
│   └── 掃描 repo 中洩漏的 Token / API Key
│
├── Dependabot Alerts
│   └── 掃描相依套件的已知漏洞 → 自動開 PR 修復
│
├── Code Scanning（CodeQL）
│   └── 靜態分析程式碼 → 偵測 SQL injection、XSS 等
│
└── Supply Chain Security
    └── SLSA（Supply-chain Levels for Software Artifacts）
        → 確保 build → release 流程不可竄改
  • Commit Signing：用 git commit -S 加上 GPG/SSH 簽署，GitHub 會在 commit 旁顯示「Verified」標記。保護分支可設定「Require signed commits」。
  • Dependabot：自動掃描 package.json、requirements.txt 等的相依套件，發現漏洞時自動開 PR 升級——你只需要 Review + Merge。
  • git filter-repo：清理 Git 歷史中的敏感資料（Token、密碼）的官方工具。比 git filter-branch 快 10-100 倍且更安全。使用前一定要備份。
  • OSSF Scorecard：GitHub 的開源專案安全評分工具，從 CI、測試、授權、漏洞管理等維度打分——可作為貢獻前的評估依據。

8.14 進階挑戰題

  1. 找一個有 good first issue 標籤的開源專案，走完「Fork → 開發 → 上游同步 → PR → Review → 合併」完整流程。記錄每一步遇到的坑和心得。
  2. 為你自己的專案設定完整的安全鏈：啟用 Secret Scanning、Dependabot、Code Scanning，並在保護分支上要求 signed commits。寫一份 200 字的「安全設定報告」。
  3. 研究 GitHub 的 Sponsor 功能和 FUNDING.yml，為你的開源專案設定贊助管道（即使只是放一個「Buy me a coffee」連結）。寫一段說明為什麼開源維護者值得被支持。

8.15 專案級端到端 Worked Example：開源專案「從個人 repo 到社群治理」專案

這是最後一哩：把單元 1–7 的全部知識串成一個完整的開源專案治理層——法律（LICENSE）、貢獻（CONTRIBUTING）、社群（CoC）、安全（SECURITY + 安全鏈）、發佈（自動 Release）、永續（FUNDING）。做完它，你的 repo 就是「一個準備好被世界使用的開源專案」。

產出檔案樹 · FILE TREE
techco-lib/
├── LICENSE                     # MIT（單元 8.2）
├── CONTRIBUTING.md             # 貢獻規範（單元 8.3）
├── CODE_OF_CONDUCT.md          # 行為守則（單元 8.4）
├── SECURITY.md                 # 漏洞回報管道
├── FUNDING.yml                 # 贊助連結（單元 8 挑戰）
├── .github/
│   ├── ISSUE_TEMPLATE/         # bug / feature（單元 5）
│   ├── CODEOWNERS              # 核心維護者（單元 4）
│   └── workflows/
│       ├── ci.yml              # 測試閘門（單元 7）
│       ├── codeql.yml          # 安全掃描（單元 8.12）
│       └── release.yml         # 打 tag 自動發佈（單元 8.5）
└── README.md                   # 門面：徽章 + 快速開始
關鍵檔案 · KEY FILES
# SECURITY.md（漏洞回報）
支援版本、如何回報（私訊 / security.txt）、
回應 SLA、已知漏洞的修補時程。

# .github/workflows/release.yml 重點
on:
  push: { tags: [ "v*" ] }
jobs:
  release:
    runs-on: ubuntu-latest
    permissions: { contents: write }
    steps:
      - uses: actions/checkout@v4
      - run: npm ci && npm test
      - run: npm publish --provenance
        env: { NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }} }
      - uses: softprops/action-gh-release@v2
驗證命令與輸出 · VERIFY
# 1. 檢查社群健康度（community health）
gh api /repos/TechCo/techco-lib/community/profile \
  --jq '{health_score, files: .files}'
# 輸出 → LICENSE、README、CONTRIBUTING、
#        CODE_OF_CONDUCT、SECURITY 全齊 → 高分

# 2. 打 tag 自動發佈
git tag v1.0.0 && git push --tags
gh release view v1.0.0 --json name,assets
# 輸出 → {"name":"v1.0.0","assets":[...]}

# 3. 安全鏈總檢
gh api /repos/TechCo/techco-lib/dependabot/alerts --jq 'length'
# 輸出 → 0（無未修依賴漏洞）

# 4. 認證 commit 比例（Verified）
git log --format='%G?' -10 | grep -c '^G'
# 輸出 → 10（10/10 為 Verified commit）
為什麼這是「專案級」：這把整門課收斂成一個「可以被世界使用的 repo」。法律文件決定別人能不能合法用、治理文件決定別人想不想參與、安全鏈決定別人敢不敢用、發佈自動化決定版本流不流暢——單元 1–7 的每個技巧，在這裡各就各位。

8.16 效能 / 品質 / 安全深度

效能 · PERFORMANCE
- 自動化釋放維護者時間：release、triage、dependabot
  都交給機器，人只做決策
- 批次管理：gh CLI 一次處理多 repo / 多 issue
- release 自動化：打 tag 即發佈，不需人工打包
- 社群回覆 SLA 靠 bot + 模板，不靠記性
- 大專案用 GraphQL / 分頁 API 控制 rate limit
品質 · QUALITY
- Community Health 分數可量化治理完整度
- Release Notes 依 PR 自動生成，格式一致
- Issue triage 制度 + 模板維持回報品質
- 文件（README / CONTRIBUTING）定期檢視
- CI 徽章公開展示品質，貢獻者一眼看懂
安全 · SECURITY
- SECURITY.md：明確漏洞回報管道與 SLA
- 安全鏈全開：Secret scanning、Dependabot、
  CodeQL、signed commits、branch protection
- 發佈加 provenance（SLSA）防供應鏈竄改
- 貢獻者不可直接 push，全部走 PR + 審查
- 意外洩漏 Token：先撤銷 > 再清理歷史（8.8 紅線）
