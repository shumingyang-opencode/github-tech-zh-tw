1.1 定義：GitHub 是什麼

GitHub 是一個程式碼託管與協作平台（code hosting & collaboration platform）——它託管你用 Git 管理的專案，並在之上提供協作、追蹤、自動化與部署服務。2008 年上線，如今超過一億開發者在上面工作。

一句話：GitHub = 「用 Git 管的程式碼」＋「放上雲端」＋「加上一群人一起開發的工具」。
對比GitGitHub
本質版本控制工具雲端託管平台
運行位置你的電腦（本機）雲端伺服器
發明Linus Torvalds（2005）GitHub, Inc.（2008）
少了它會怎樣GitHub 無法運作Git 照樣能用（只是單機）

1.2 Git 與 GitHub 的關係

很多人把兩者混為一談，其實它們是分層合作的：

  • Git：分散式版本控制系統（DVCS）。負責在你本機記錄「每一次變更」，讓你能回到任何一個歷史版本。
  • GitHub：把 Git repo 放到雲端，提供多人共用的一份中心副本，加上網頁介面、Issue、PR、Actions 等服務。
Git · 本機工具
git init
git add .
git commit -m "first"
GitHub · 雲端平台
git push -u origin main
# 之後：Issues、PR、
# Pages、Actions…
記憶法：Git 是「引擎」，GitHub 是「車子」——引擎讓車跑，車子讓引擎被人用到。沒有 GitHub，Git 依然能幫你管理檔案；有了 GitHub，Git 才變成「一群人協作」的工具。

1.3 GitHub 提供什麼：平台功能地圖

GitHub 不是「一個放程式碼的地方」，而是一整套開發工作流。五大核心服務：

功能用途單元
Repo 託管程式碼雲端備份、版本歷史、分支單元 2
Pull Request程式碼審查與合併流程單元 4
Issues / Projectsbug 追蹤、任務管理、看板單元 5
GitHub Pages靜態網站免費部署單元 6
GitHub ActionsCI/CD 自動化單元 7

1.4 社群價值：為什麼大家都用 GitHub

  1. 業界標準：徵才、作品集、公司內部，無處不在。
  2. 開源入口：全球最大的程式碼社群——你眼前的教學站也開源在 GitHub。
  3. 可回溯、可審查：每一行程式碼的歷史與討論都有記錄。
  4. 免費額度充足：公開 repo 免費；私有 repo 也有免費方案。
  5. 生態系：Actions、Copilot、Codespaces、Marketplace 一應俱全。

1.5 帳號與認證 · Authentication

註冊後，你的 repo 網址形如 https://github.com/你的帳號/repo名。連上 GitHub 有三種認證方式：

方式原理適合
HTTPS + PATPersonal Access Token 當密碼最常見、容易設定
SSH key一對公私鑰，免密碼長期使用、最安全
gh CLI命令列登入，同時管理認證重度命令列使用者
Token 安全紅線：Token / 金鑰永遠不要提交進 repo 或寫在程式碼裡。萬一洩漏：① 到 GitHub Settings → Developer settings 立即撤銷（revoke）；② 若已進 Git 歷史，用 git filter-repo 清理（見單元 8）。

1.6 Worked Example：從註冊到第一次 push

步驟 · STEPS
1. 到 github.com 註冊帳號（選 username）
2. Settings → Developer settings → PAT
   → 產生並複製（只顯示一次！）
3. 本機設定身份
   git config --global user.name "你的名字"
   git config --global user.email "你的email"
4. 建立測試 repo 並 push（詳見單元 2）
驗收 · CHECKLIST

✅ 能登入 github.com
✅ 已產生 PAT 或 SSH key
✅ git config --list 看得到身份
✅ 成功 push 過一次
✅ 知道 Token 該存在哪裡（密碼管理員）

實作上，gh auth login（單元 8）一次就搞定 PAT + 身份設定，新手最推薦。

1.8 常見錯誤與陷阱

最常見的誤解：以為「Git = GitHub」。面試與文件常考兩者差別——Git 是工具、GitHub 是平台，一定要能分清楚。
用「帳號密碼」push 卻一直失敗：GitHub 於 2021 年後不再接受密碼做 git push，一律要用 PAT 或 SSH。密碼驗證失敗時，記得改用 Token。
練習：在本機執行 git --version；若沒安裝，到 git-scm.com 下載。然後設定你的 user.name / user.email，為單元 2 做準備。

1.9 進階真實情境 Worked Example：Organization 建立與多 Repo 安全治理

情境 · SCENARIO
你是新創團隊 TechCo 的第一位工程師，
負責建立 GitHub Organization，
設定 SAML SSO、Branch Protection、
Secret Scanning，並用 gh CLI 批次建立
三個 repo（frontend / backend / infra）。
完整操作 · COMMANDS
# 1. gh CLI 登入並設定身份
gh auth login
gh auth setup-git

# 2. 用 API 建立 Organization
gh api --method POST /orgs \
  -f login=TechCo \
  -f name="TechCo Inc." \
  -f billing_email="admin@techco.dev"

# 3. 批次建立三個 repo
for svc in frontend backend infra; do
  gh repo create "TechCo/$svc" --private \
    --description "$svc service"
done

# 4. 為每個 repo 開啟 Secret Scanning
for svc in frontend backend infra; do
  gh api --method PUT \
    "/repos/TechCo/$svc" \
    -f security_and_analysis='{"secret_scanning":{"status":"enabled"}}'
done

# 5. 設定 Branch Protection（main）
gh api --method PUT \
  "/repos/TechCo/backend/branches/main/protection" \
  -f required_status_checks='{"strict":true,"contexts":["test"]}' \
  -f enforce_admins=true \
  -f required_pull_request_reviews='{"required_approving_review_count":2}'
為什麼選這個方法：Organization 讓你用統一的身份、權限、安全策略管所有 repo——比「每個人各管各的」安全十倍。用 gh API 批次操作比手動在 UI 上逐一設定快 10 倍，而且可重現、可版本化。

1.10 深入原理擴充

GitHub 架構 · ARCHITECTURE
Git（本機）──HTTPS/SSH──▶ GitHub.com（Git 服務）
                                    │
                    ┌───────────────┼───────────────┐
                    ▼               ▼               ▼
               Issues / PR      Actions         Pages
              （MySQL 資料庫）  （Runner VM）  （CDN + S3）
                    │
                    ▼
               GitHub API v3 / GraphQL v4
               （REST + GraphQL 雙介面）
  • Git over HTTPS：用 credential helper 做認證，每次 fetch/push 都帶 HTTP Basic Auth（PAT 當密碼）。GitHub 於 2021 年強制要求 PAT，不再接受帳密。
  • Git over SSH：用公私鑰挑戰-回應。SSH 連線建立後不需每次輸入密碼，但金鑰要存好——公鑰上傳到 Settings → SSH keys。
  • OAuth 2.0 流程：gh auth login 背後觸發 OAuth device flow：CLI 跳出瀏覽器 → 授權 → 取得 access token → 存在本機 credential store。
  • API Rate Limit：未認證 60 次/小時，認證後 5,000 次/小時。用 gh api /rate_limit 可查剩餘。
容易踩的坑：
  • PAT 建立時「權限範圍（scope）」決定能做什麼——repo（讀寫 repo）、workflow（改 Actions）、admin:org（管理 org）。權限太少會在 API 呼叫時收到 403。
  • SSH key 有 ed25519 與 RSA 兩種，ed25519 更安全且更快——用 ssh-keygen -t ed25519 產生。
  • GitHub 支援同一帳號綁多把 SSH key，但不支援同一把 key 綁多個帳號——每台機器一把 key，分別上傳。

症狀可能原因解決方案

1.12 進階挑戰題

  1. 用 gh CLI 建立一個 GitHub Organization，包含 3 個 repo，並為所有 repo 啟用 Branch Protection（require 1 approve + CI pass）。截圖 Settings 頁面作為完成證明。
  2. 產生一把 ed25519 SSH key，加到 GitHub 帳號，測試 ssh -T git@github.com 顯示「Hi username!」。然後再產生一把 key 加到你的 Organization，測試兩把 key 在不同 repo 的行為差異。
  3. 研究 GitHub OAuth App 與 GitHub App 的差異（從 Settings → Developer settings），寫一段 150 字說明你會在什麼場景選擇哪一種。

1.13 專案級端到端 Worked Example：TechCo 公司 GitHub 基礎建設專案

把本單元的知識（平台、認證、Organization、安全治理）放大到整家公司的規模：所有設定都寫成程式碼（Infrastructure as Code），放進一個 techco-infra repo，讓「公司怎麼用 GitHub」也可以審查、版本化、重現——這是單元 1.9「單一 repo 治理」之上的整站層級。

產出檔案樹 · FILE TREE
techco-infra/
├── .github/
│   ├── CODEOWNERS            # 設定變更需 DevOps 審查
│   └── workflows/
│       └── audit.yml         # 每晚稽核「設定有沒有漂移」
├── scripts/
│   ├── bootstrap-org.sh      # 一次性初始化（延伸 1.9）
│   └── apply-policies.sh     # 把策略套到所有 repo
├── policies/
│   ├── org.yml               # org 層級規則
│   └── branch-protection.json# 標準保護分支設定
└── README.md
關鍵檔案 · KEY FILES
# policies/branch-protection.json（片段）
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["ci"]
  },
  "required_pull_request_reviews": {
    "required_approving_review_count": 2
  },
  "enforce_admins": true
}

# scripts/apply-policies.sh（核心迴圈）
for repo in $(gh repo list TechCo \
  --json name --jq '.[].name'); do
  gh api --method PUT \
    "/repos/TechCo/$repo/branches/main/protection" \
    --input policies/branch-protection.json
done
驗證命令與輸出 · VERIFY
# 1. 驗證所有 repo 的保護分支都生效
gh api /repos/TechCo/backend/branches/main/protection \
  --jq '.required_pull_request_reviews.required_approving_review_count'
# 輸出 → 2

# 2. 稽核成員 2FA 狀態（org 稽核 log）
gh api "/orgs/TechCo/audit-log" --paginate \
  --jq '.[] | select(.action=="org.two_factor_requirement_enabled")' | head -1
# 輸出 → {"action":"org.two_factor_requirement_enabled", ...}

# 3. 全公司 repo 清單與可見性
gh repo list TechCo --limit 100 --json name,visibility
# 輸出 → [{"name":"backend","visibility":"PRIVATE"}, ...]
為什麼這是「專案級」：單元 1.9 只設定單一 repo；這裡把整間公司當成一個專案在治理——用程式碼管策略、用 CI 稽核漂移、用 CODEOWNERS 讓重大變更有人把關。規模越大，「人按 UI 慢慢點」越不可行，改成「程式碼 + 自動化」才是正解。

1.14 效能 / 品質 / 安全深度

效能 · PERFORMANCE
# 傳輸與 API 面
- git clone 用 SSH 比 HTTPS 少一層認證往返
- API rate limit：認證 5,000 次/小時，批次優先
- 大 repo 用 --filter=blob:none 只拉需要的物件
- LFS 檔案走獨立 CDN，不卡 Git 傳輸
# 回報與儀表板
- github.com/status 查平台可用性
- gh api /rate_limit 檢查剩餘額度
品質 · QUALITY
平台層品質由 GitHub 保證（SLA、Status Page），
你這一層的品質是「設定品質」：
- 每條規則都有人負責（CODEOWNERS）
- 設定進 repo：可 diff、可 review
- 稽核 workflow 每天抓「設定漂移」
- 新 repo 用預設範本（repo template）
  自動帶上安全設定，避免「開局就裸奔」
安全 · SECURITY
安全由上到下三層：
1. 身份層：SAML SSO + 強制 2FA
2. 存取層：最小權限 + 保護分支
3. 內容層：Secret Scanning + push protection
紅線：PAT 只用最小 scope、不放進 repo、
失效立刻撤銷；金鑰一律存密碼管理員。
