4.1 定義：Pull Request 是什麼

直接把分支 merge 進 main 很危險。GitHub 的答案是 Pull Request（PR）：一個「請求把某分支合併進另一分支」的審查流程。它不是 Git 指令，而是 GitHub 的協作機制。

PR 流程 · WORKFLOW
1. 開分支 → 開發 → push
2. 在 GitHub 開 Pull Request（feature → main）
3. 隊友 Review：討論、留言、改進
4. 通過檢查 → 合併 Merge
5. 完成！功能進入 main
核心價值：PR 讓「合併程式碼」變成「有記錄、有審查、可回顧」的過程——每次合併都有討論串、每行程式碼都能被檢視、出問題能查到是哪個 PR 引入的。

4.2 如何開一個 PR

  1. 確認你的分支已 git push 到 GitHub。
  2. repo 頁會出現綠色「Compare & pull request」按鈕。
  3. 確認 base（要合進哪：通常是 main）與 compare（你的分支）。
  4. 寫標題與描述，按 Create pull request。
base / compare · 方向要對
base: main     <-   compare: feature/greeting

方向：把 compare 合進 base。
反了 = 把 main 合進 feature，結果完全相反。
PR 描述建議：「改了什麼」＋「為什麼改」＋「怎麼測試」——讓 reviewer 不用猜。可用 Markdown 排版（複習我們的 GFM 單元）。

4.3 Code Review：程式碼審查

Reviewer 在 PR 的「Files changed」分頁逐行檢視與留言。審查結果有三種：

審查動作意義
Comment一般留言，不阻擋合併
Request changes需要修正後再合併（擋住）
Approve同意合併
被 review 的心態：Review 是「一起把程式寫好」，不是批評。提問式建議（「這裡是不是該考慮…？」）比命令式更受歡迎；被要求修改時，改完直接 push 到同一分支，PR 會自動更新。

4.4 討論與指派 · Conversation & Assignee

  • Conversation 分頁：PR 的主要討論串，可用 @mention 標記隊友。
  • Reviewers：指名誰來審（點右欄 Add reviewers）。
  • Assignees：指派誰負責這支 PR。
  • Draft PR：還沒做完先開「草稿」，不會被誤合併。
小技巧：在 Review 留言中輸入 /cc @隊友 或直接建議修改（suggestion block）——reviewer 可以「提出具體改法」，作者按一下就能套用。

4.5 關聯 Issue · Linking Issues

在 PR 描述寫 Closes #12，合併時 GitHub 會自動關閉 issue 12。這是「任務 → 程式」連結的關鍵。

PR 描述 · DESCRIPTION
修正登入頁空白問題。

- 加上欄位驗證
- 修正錯誤訊息

Closes #12

關鍵字：fixes、closes、resolves，後面接 #issue編號。

4.6 三種合併方式

方式效果何時用
Merge commit保留所有 commit 與「合併事件」節點想完整保留歷史、可回溯
Squash and merge把整條分支壓成一個 commit功能分支（最常見），歷史乾淨
Rebase and merge線性重放 commit，無合併節點想維持「一條直線」的線性歷史
歷史長相 · HISTORY
Merge commit:   o──o─┬─o──o──o
                        └──────┘（有合併節點）

Squash:         o──o──[1 commit]──o（功能濃縮成一筆）

Rebase:         o──o──o──o──o（完全線性）
團隊要統一：三種方式產生的歷史長相不同，混用會讓 git log 難以閱讀。開源專案多用 Squash；嚴謹維護歷史的專案用 Merge commit 或 Rebase。定了就別常換。

4.7 保護分支 · Protected Branches

防止有人直接 push main，強制「必須 PR + review 才能合併」。設定：

設定位置 · SETTINGS
Repo → Settings → Branches → Branch protection rules
├── Require a pull request before merging
├── Require approvals（至少 1 人 Approve）
└── Require status checks（CI 通過才合併，見單元 7）
為什麼重要：沒有保護分支，任何人都能直接動 main——一個誤 push 就能讓整條主線壞掉。正式專案必開；個人專案養成習慣也開。

4.8 Worked Example：完成一次 PR

步驟 · STEPS
1. git checkout -b fix/login-validation
2. 修改程式 → add → commit → push -u origin ...
3. GitHub 出現 Compare & pull request
4. 寫描述 + "Closes #12" → Create
5. 請隊友 Approve
6. 選 Squash and merge → Confirm
7. 回到本機：git checkout main && git pull
驗收 · ACCEPT

✅ PR 狀態顯示 Merged
✅ Issue #12 自動關閉
✅ main 已有新功能
✅ git log 歷史乾淨

練習：把單元 2 的 repo 開一支 docs/readme 分支，改 README，開一支 PR，練習「開 → 討論 → 合併 → 清理」完整流程。

  • 用 Closes #12 把 PR 與 issue 串起來。
