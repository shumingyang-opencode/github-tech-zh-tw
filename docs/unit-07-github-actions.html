7.1 定義：GitHub Actions 是什麼

GitHub Actions 讓你在「特定事件發生時」自動跑工作流程——最常見的就是 CI/CD：程式碼 push 後自動測試、建置、部署。CI（持續整合）＝每次變更自動檢查；CD（持續部署）＝檢查通過自動上線。

一句話：Actions = 「在 GitHub 的雲端機器上，自動執行你寫好的劇本」。

7.2 核心概念：五個名詞

名詞意義
Workflow一個自動化流程，寫在 .github/workflows/*.yml
Event觸發條件（push、pull_request、schedule…）
Job一個工作單位（在一台 runner 上跑）
StepJob 裡的一步（跑指令或呼叫 action）
Action可重用的步驟套件（Marketplace 下載）
Runner執行環境（ubuntu-latest 等虛擬機）
階層關係 · HIERARCHY
Workflow（檔案）
└── on（事件）
└── jobs
    └── job A（runner 1）
        ├── step 1：uses 某 action
        └── step 2：run 某指令
    └── job B（runner 2，可並行）

7.3 第一個 Workflow · Hello CI

放在 .github/workflows/ci.yml：

.github/workflows/ci.yml
name: CI
on:
  push:
    branches: [main]
  pull_request:

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
      - run: npm ci
      - run: npm test
解讀：push 到 main 或有人開 PR 時 → 開一台 ubuntu 虛擬機 → 依序執行 checkout（抓程式碼）、裝 Node、裝相依、跑測試。任何一步失敗，workflow 就顯示紅色。可到 repo 的 Actions 分頁看執行結果與 log。

7.4 觸發事件 · Events 全覽

on · EVENTS
on:
  push:                  # push 時
  pull_request:          # 開/更新 PR 時
  schedule:              # 定時（cron）
    - cron: "0 3 * * *"   # 每天凌晨 3 點
  workflow_dispatch:     # 手動按鈕
  issues:                # issue 事件

cron 語法為「分 時 日 月 週」五段。0 3 * * * = 每天凌晨 3 點。手動觸發（workflow_dispatch）在 Actions 分頁按「Run workflow」。

7.5 常用 Action

Action用途
actions/checkout把 repo 程式碼抓到 runner（幾乎每個 workflow 第一步）
actions/setup-node / setup-python安裝指定語言環境
actions/cache快取相依套件，加速 CI
actions/upload-artifact / download-artifact上傳/下載建置產物（跨 job）
actions/deploy-pages部署到 GitHub Pages（單元 6）
dependabot（內建）自動更新相依套件並開 PR（單元 8）

7.6 Secrets：機密變數

workflow 需要 API key、Token 時，不要寫死在 YAML——寫進去就等於公開給所有能看到 repo 的人。用 Secrets 加密存放：

設定與使用 · SETUP & USE
# 設定：Settings → Secrets and variables → Actions
# 名稱如：MY_API_KEY

# 使用：在 workflow 中以 ${{ secrets.MY_API_KEY }} 引用
env:
  API_KEY: ${{ secrets.MY_API_KEY }}
安全：Secrets 不會顯示在 log 中，但不要自己 echo 它——「echo $API_KEY」這種 debug 動作會把機密印出來，GitHub 有時會事後遮罩，但別賭。

7.7 把 CI 當檢查閘門 · Status Checks

把 workflow 接上「保護分支」（單元 4），PR 的 CI 沒通過就不能合併——這是團隊品質的第一道防線：

保護分支設定 · SETTINGS
Settings → Branches → Branch protection
├── Require status checks to pass
└── 勾選你的 workflow 名稱（如「test」）
為什麼是「閘門」：未通過的 PR 無法合併 → 壞程式碼進不了 main → main 永遠「已知可跑」。這正是 CI 的核心價值。

7.8 進階：快取、Matrix、Artifact

matrix · 多版本測試
strategy:
  matrix:
    node-version: [18, 20, 22]
    os: [ubuntu-latest, macos-latest]
# 產生 3×2 = 6 台 runner 平行跑，確保多環境相容
cache · 加速
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: ${{ runner.os }}-npm-${{ hashFiles('package-lock.json') }}

7.9 Worked Example：完整 CI + 自動部署

練習 · PRACTICE
1. 新增 .github/workflows/ci.yml
   - on push + pull_request
   - job test：checkout + setup-node
     + npm ci + npm test
2. 開 PR 測試 CI 是否啟動
3. 故意改壞一行 → CI 紅 → 修回 → 綠
4. 到 Settings → Branches 勾 Require status checks
驗收 · ACCEPT

✅ PR 上看到 CI 通過
✅ 壞 PR 無法合併（閘門生效）
✅ Actions 分頁看得到執行歷史
✅ Matrix 有多環境時全部通過

練習：為你的 repo 加一份 CI，並故意「先紅再綠」一次——親眼看到 CI 擋住壞 PR，比任何解釋都有效。
看完這單元你應該能說出：
  • 說出 Workflow / Job / Step / Action / Runner 的關係。
  • 寫出一份最小的 CI workflow。
  • 用 on 設定 push / PR / 排程 / 手動觸發。
  • 正確使用 Secrets 保護機密，並知道 log 洩漏的風險。
  • 用 status checks 把 CI 變成 PR 的合併閘門。

7.10 進階真實情境 Worked Example：多 Job 矩陣測試 + Artifact 上傳 + 自動發佈

情境 · SCENARIO
你是一個開源 CLI 工具的維護者，
需要在每次 PR 上：
- 在 3 個 OS × 3 個 Node 版本 = 9 台 runner 測試
- 測試通過後上傳 build artifact
- 合併到 main 時自動發佈 npm 套件
.github/workflows/ci.yml · 完整版
name: CI + Release
on:
  push: { branches: [main] }
  pull_request:

jobs:
  test:
    runs-on: ${{ matrix.os }}
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
        node: [18, 20, 22]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: ${{ matrix.node }} }
      - run: npm ci
      - run: npm test
      - uses: actions/upload-artifact@v4
        if: ${{ matrix.os == 'ubuntu-latest' }}
        with:
          name: dist
          path: dist/

  release:
    needs: test
    if: ${{ github.ref == 'refs/heads/main' }}
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 22, registry-url: https://registry.npmjs.org }
      - run: npm publish --provenance
        env:
          NODE_AUTH_TOKEN: ${{ secrets.NPM_TOKEN }}
為什麼選這個方法：矩陣測試在 9 台 runner 上同時驗證跨平台相容性——任何一台紅了就代表有問題。Artifact 讓你在不同 job 間傳遞建置產物（測試 job 建好 → release job 發佈）。Release job 只在 main 分支上跑，確保 PR 不會誤發佈。

7.11 深入原理擴充

Runner 架構 · HOW IT WORKS
GitHub Actions Runner 架構：

┌─────────────────────────────────┐
│ GitHub.com                       │
│ └── Event Queue                  │
│     └── Workflow Run (待派送)     │
└────────────┬────────────────────┘
             │ 調度
┌────────────▼────────────────────┐
│ Runner VM（Ubuntu / macOS / Win）│
│ └── Runner Application（程式）    │
│     └── 執行 Step（依序）        │
│         ├── uses: action@v4     │
│         │   └── Node.js 子程序   │
│         └── run: npm test       │
│             └── Shell 子程序     │
└─────────────────────────────────┘
  • Self-hosted Runner：你可以架設自己的 runner 在公司內網——適合需要存取內部資源、使用特定硬體（GPU）、或降低成本的場景。
  • Workflow Runs 的隔離：每個 workflow run 在一台全新的 VM 上執行（無狀態），之前的 run 不會留下任何痕跡——這是「可重現性」的基礎。
  • Composite Actions：可以把多個 step 包成一個可重用的 action，放在同一個 repo 的 .github/actions/ 資料夾。比 Marketplace 上的 action 更輕量、更可定制。
  • Reusable Workflows：一個 workflow 可以呼叫另一個 workflow（uses: ./.github/workflows/ci.yml），避免重複 YAML——大型專案的必備技巧。

7.12 診斷式疑難排解表

症狀可能原因解決方案
Workflow 完全沒觸發YAML 檔案位置錯 / 觸發條件不對確認 .github/workflows/ 資料夾正確；on.push.branches 包含目標分支
Unrecognized named-value: "secrets"Secrets 在 PR 的 fork 中不可用改用 pull_request_target（有安全風險）或在 workflow 中做條件判斷
Matrix 測試其中一台紅了跨平台相容問題查看該 job 的 log；用 if: matrix.os == 'ubuntu-latest' 限制只在特定 OS 執行某 step
Error: Input required and not supplied: node-versionsetup-node 參數格式錯確認 with: 底下有正確縮排（2 空格）
Artifact 上傳失敗路徑不存在在 upload-artifact 前先 ls dist/ 確認目錄存在

  2. 研究 workflow_dispatch 的 inputs 功能，建立一個手動觸發的 workflow，讓你在 Actions 頁面輸入參數（如環境名稱、版本號），workflow 根據輸入執行不同分支。

7.14 專案級端到端 Worked Example：完整 CI/CD 平台專案

單元 7.10 是一條 workflow 的矩陣測試；這裡把 CI/CD 放大成整個平台的流水線：可重用 action、相依快取、多服務矩陣、安全掃描、部署與發佈串成一條鏈。做完它，你的 repo 就是「推上 main 就自動走完整套品管」的狀態——這是單元 7.10 之上的平台架構設計。

產出檔案樹 · FILE TREE
techco-app/
├── .github/
│   ├── actions/
│   │   └── setup-env/          # 共用「裝環境 + 快取」action
│   └── workflows/
│       ├── ci.yml              # 閘門：lint + test + build
│       ├── security.yml        # CodeQL + 依賴掃描
│       └── release.yml         # 打 tag → 建置 → 發佈
├── services/
│   ├── api/                    # Python 服務
│   ├── web/                    # Node 服務
│   └── worker/                 # Rust 服務
└── README.md                   # 內含 CI 狀態徽章
關鍵檔案 · KEY FILES
# .github/workflows/ci.yml 重點
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix: { service: [api, web, worker] }
    steps:
      - uses: actions/checkout@v4
      - uses: ./.github/actions/setup-env
        with: { service: ${{ matrix.service }} }
      - run: make test-${{ matrix.service }}
      - uses: actions/cache@v4        # 相依快取
        with:
          path: ~/.cache
          key: ${{ matrix.service }}-${{ hashFiles('**/lock*') }}
驗證命令與輸出 · VERIFY
# 1. 跑一次完整 CI（3 服務平行）
gh run list --workflow ci.yml --limit 1 \
  --json status,conclusion,displayTitle
# 輸出 → {"status":"completed","conclusion":"success",...}

# 2. 快取命中（第二次跑更快）
gh run view <run-id> --json jobs \
  --jq '.jobs[].steps[] | select(.name|contains("cache")) | .conclusion'
# 輸出 → success（且 log 顯示 Cache hit）

# 3. 安全掃描結果
gh api /repos/TechCo/app/code-scanning/alerts --jq 'length'
# 輸出 → 0（無未修漏洞）

# 4. Release 產物
gh release view v2.0.0 --json assets --jq '.assets[].name'
# 輸出 → techco-api_2.0.0.tar.gz ...
為什麼這是「專案級」：單元 7.10 是一條 workflow；這裡是「CI/CD 平台的架構」。共用 action 消除重複、快取節省時間與額度、安全掃描內建進閘門、發佈自動化——這些設計決定了一個團隊每天能迭代多快、多安全。

7.15 效能 / 品質 / 安全深度

效能 · PERFORMANCE
- 相依快取：key 用 hashFiles 鎖定內容，
  命中時省下數分鐘與額度
- Matrix 平行：多 OS / 多版本同時跑
- concurrency 取消「過時的 run」，
  避免堆積浪費額度
- 重度建置可改用 container 或 self-hosted runner
- 快取 key 記得在依賴變更時自動失效
品質 · QUALITY
- 用 reusable workflows / composite actions
  消除 YAML 重複，規則只寫一次
- Status check 當閘門：沒過就不能合併
- Artifact 保存測試報告 / 建置產物，供事後檢討
- action 固定到 tag 或完整 SHA（可重現）
- README 放 CI 徽章，品質對外可見
安全 · SECURITY
- Secrets 放 Settings：repo / org / 環境三層
- GITHUB_TOKEN 最小權限（permissions 明確宣告）
- 別在 fork 的 PR 上執行未受信任程式碼
  （pull_request_target 有 SSRF / 注入風險）
- action 一律固定版本或 SHA，防供應鏈竄改
- Dependabot 掃依賴 + CodeQL 掃程式碼，
  納入閘門（單元 8 會再深談）
